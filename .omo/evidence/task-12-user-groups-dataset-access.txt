IMPLEMENTATION NOTES
  - Endpoints used (all from T10 ApiConfig): adminUsers (GET list), createAdminUser (POST),
    updateAdminUser (PATCH; edit fields + is_active toggle + is_admin), deleteAdminUser (DELETE),
    adminUserGroups (GET current membership when opening the assign modal),
    updateAdminUserGroups (PUT selection), plus adminGroups (GET org groups for the checkbox list).
  - Table: DataTable from @humansignal/ui (repo ds lint rule `ds/raw-control` forbids raw <table>;
    explicit column sizes set after a browser pass caught 150px-default overflow).
    Columns: Email, Name, Groups, Status (Active/Inactive Badge), Role (Admin Badge / Member),
    Last Activity, row actions (Dropdown.Trigger + Menu contextual).
  - Create/edit/assign modals: ModalWindow (@humansignal/ui, renders in the owner's React tree so
    the app ApiContext reaches the body); delete uses ConfirmDialog (DangerZone-style confirmation).
    Form inputs use the app Form Input; errors render as Message variant="negative" inline.
  - Owner protection: the T10 API does not expose an owner flag, so the client disables Delete for
    the lowest-id is_admin user (the owner is the first admin created in the org) and for yourself;
    the authoritative guard remains server-side (403 "The organization owner cannot be deleted" /
    "You cannot delete yourself"), and the failure message is surfaced verbatim if ever reached.
  - Error handling: mutations run with suppressError so the page owns the failure surface
    (validation_errors > detail > field strings > status name); the list load uses the global
    handler plus an inline "Could not load users." + Retry state. No crash paths: every callApi
    result is null/array-guarded.
  - Non-admin gate: AdminLayout (T11) redirects; UsersPage assumes admin context (asserted in tests).
